# 性能基准测试

本文档记录企业级 RAG 知识库在标准测试环境下的性能基准数据，覆盖检索延迟、问答端到端延迟、文档解析吞吐、图谱查询性能、消融实验、分块策略对比、混合检索对比与压测数据，并给出调优建议。所有数据均可复现，复现脚本位于 `benchmarks/` 目录。

## 1. 测试环境

### 1.1 硬件配置

| 项 | 规格 |
|----|------|
| CPU | AMD EPYC 7763 64 核 / 128 线程 |
| 内存 | 256 GB DDR4 3200MHz |
| 磁盘 | 2 TB NVMe SSD |
| GPU | NVIDIA A10 24GB（用于嵌入与精排加速） |
| 网络 | 内网万兆 |

### 1.2 软件版本

| 组件 | 版本 |
|------|------|
| OS | Ubuntu 22.04 LTS |

| Milvus | 2.4.0 |

| Redis | 7.2 |
| Python | 3.11 |

### 1.3 数据集规模

| 数据 | 规模 |
|------|------|
| 文档总数 | 12,000 篇（PDF / Word / 图片混合） |
| 分块总数 | 1,024,800 个 |

| 图谱节点 | 102,400 个 |

| 评测集 | 32 道标注问题（含 gold chunk 与相关性分级） |

### 1.4 测试方法

- 延迟测试：每接口连续请求 10,000 次，剔除前 1,000 次预热，统计 P50/P95/P99。
- 吞吐测试：固定并发逐步加压，记录稳定吞吐与资源水位。
- 消融实验：在评测集上对每种策略跑全量检索，计算 Recall@K / MRR / NDCG@K / Precision@K。
- 压测工具：Locust，每虚拟用户独立 Token，会话隔离。

## 2. 检索性能

### 2.1 向量检索（Milvus）

100 万向量，IVF_FLAT 索引（`nlist=1024`），检索参数 `nprobe=16`，Top-20 召回。

| 指标 | 延迟 |
|------|------|
| P50 | 18 ms |
| P95 | 48 ms |
| P99 | 72 ms |
| QPS（单节点） | 2,100 |

对比 HNSW 索引（`M=16`, `efConstruction=200`, `ef=64`）：P95=22ms，QPS=4,800，召回率（Recall@10 vs 暴力搜索）0.982。HNSW 延迟与吞吐更优但内存占用约为 IVF_FLAT 的 1.6 倍，内存受限场景选 IVF_FLAT，延迟敏感场景选 HNSW。

### 2.2 BM25 检索

Elasticsearch 集群（3 节点），104 万文档，Top-20 召回。

| 指标 | 延迟 |
|------|------|
| P50 | 9 ms |
| P95 | 22 ms |
| P99 | 38 ms |
| QPS | 6,500 |

### 2.3 混合检索端到端

向量 + BM25 并行检索 + RRF 融合（不含精排）。

| 指标 | 延迟 |
|------|------|
| P50 | 26 ms |
| P95 | 55 ms |
| P99 | 89 ms |

混合检索 P95（55ms）接近两路中较慢的一路（向量 48ms）+ 融合开销，得益于并行执行。

## 3. 问答性能

端到端问答含限流、缓存、改写、检索、重排、生成、溯源全链路。LLM 为 DeepSeek（远端 API）。

| 场景 | P50 | P95 | P99 | 说明 |
|------|-----|-----|-----|------|
| 缓存命中 | 6 ms | 9 ms | 14 ms | 直接返回缓存答案 |
| 缓存未命中（含生成） | 1.2 s | 1.8 s | 2.6 s | 含 LLM 生成 + 溯源 |
| offline 模式（无生成） | 180 ms | 280 ms | 420 ms | 仅检索 + 片段拼接 |

问答链路各阶段耗时分解（缓存未命中场景，P95）：

| 阶段 | 耗时 | 占比 |
|------|------|------|
| 限流 + 鉴权 | 3 ms | 0.2% |
| 缓存查询 | 4 ms | 0.2% |
| Query 改写（LLM） | 220 ms | 12.2% |
| 三路检索（并行） | 55 ms | 3.1% |
| ACL 过滤 + RRF 融合 | 8 ms | 0.4% |
| Cross-Encoder 精排 | 14 ms | 0.8% |
| LLM 生成 | 1,420 ms | 78.9% |
| 溯源标注 + 写缓存 | 76 ms | 4.2% |

LLM 生成占端到端耗时的近 80%，是优化重点。Query 改写占用一次额外 LLM 调用，可通过规则化改写或缓存改写结果降低。

## 4. 文档解析吞吐

4 个 Celery Worker 并发（每 Worker `--concurrency=4`，共 16 并发任务），向量化走 GPU 批量嵌入。

| 文档类型 | 平均大小 | 单文档耗时 | 吞吐 |
|----------|----------|-----------|------|
| 文本层 PDF | 2.4 MB | 1.1 s | — |
| 扫描版 PDF（含 OCR） | 5.8 MB | 6.2 s | — |
| Word | 1.2 MB | 0.8 s | — |
| 混合负载 | 3.1 MB | 2.5 s | **120 MB/min** |

瓶颈分析：扫描版 PDF 的 PaddleOCR 占单文档耗时 60% 以上。纯文本 PDF 解析吞吐可达 320 MB/min，OCR 文档比例越高整体吞吐越低。建议将 OCR Worker 独立队列，避免拖慢文本类文档入库。

## 5. 图谱查询性能

Neo4j 单节点，10.2 万节点 / 15.7 万关系。

| 查询类型 | P50 | P95 | P99 |
|----------|-----|-----|-----|
| 单跳（节点属性查询） | 6 ms | 18 ms | 31 ms |
| 双跳（一度关系遍历） | 14 ms | 42 ms | 68 ms |
| 三跳（多跳关系推理） | 28 ms | 85 ms | 142 ms |

三跳 P95=85ms，远低于 LLM 生成延迟，验证了 GraphRAG 作为第三路召回的延迟代价可接受。三跳 P99 升至 142ms，主要来自少数大度数节点的扇出放大，通过 `LIMIT` 与索引约束可控制。

## 6. 消融实验

在种子评测集（32 题）上对比 5 种检索策略 × 4 个指标，K=5。详见 [RAG 流水线文档](./rag-pipeline.md) 第 8 节策略定义。

| 策略 | Recall@5 | MRR | NDCG@5 | Precision@5 | P95 延迟 |
|------|----------|-----|--------|-------------|----------|
| vector_only | 0.72 | 0.55 | 0.61 | 0.48 | 28 ms |
| bm25_only | 0.66 | 0.49 | 0.54 | 0.42 | 12 ms |
| rrf | 0.85 | 0.68 | 0.74 | 0.61 | 35 ms |
| full（含精排） | 0.88 | 0.72 | 0.79 | 0.66 | 52 ms |
| **full_with_terminology** | **0.91** | **0.76** | **0.83** | **0.70** | 55 ms |

### 6.1 按问题类型拆分

将种子评测集按问题跳数拆分（单跳事实 18 题 / 双跳关联 9 题 / 三跳推理 5 题），对比 `full_with_terminology` 策略：

| 问题类型 | Recall@5 | MRR | NDCG@5 | Precision@5 |
|----------|----------|-----|--------|-------------|
| 单跳（语义类） | 0.93 | 0.79 | 0.86 | 0.73 |
| 双跳（关系类） | 0.86 | 0.71 | 0.77 | 0.64 |
| 三跳（混合类） | 0.88 | 0.74 | 0.81 | 0.68 |

双跳/三跳问题召回相对低，主因是图谱覆盖率不足（部分文档实体未被抽取）。提升图谱覆盖率是后续优化方向。生产环境扩充评测集规模后可获得更稳定统计。

## 7. 分块策略对比

固定检索链路（full_with_terminology），对比三种分块策略：

| 分块策略 | 平均 chunk 长度 | chunk 总数 | Recall@5 | MRR | NDCG@5 |
|----------|-----------------|-----------|----------|-----|--------|
| 固定长度 chunk_size=512, overlap=64 | 512 | 1,024,800 | 0.68 | 0.52 | 0.58 |
| 句子切分（按句号） | 180 | 1,842,000 | 0.74 | 0.58 | 0.63 |
| **标题层级 + 段落语义（默认）** | 460 | 1,106,200 | **0.91** | 0.76 | 0.83 |

标题层级分块在召回率上显著领先。固定长度切分会破坏语义边界，导致跨块问题召回差；句子切分 chunk 过短，向量表征不稳定且上下文不足。

## 8. 混合检索 vs 单路

固定分块策略（标题层级），对比检索策略：

| 检索策略 | Recall@5 | MRR | NDCG@5 | Precision@5 | P95 延迟 |
|----------|----------|-----|--------|-------------|----------|
| 向量 only | 0.72 | 0.55 | 0.61 | 0.48 | 28 ms |
| BM25 only | 0.66 | 0.49 | 0.54 | 0.42 | 12 ms |
| RRF 融合 | 0.85 | 0.68 | 0.74 | 0.61 | 35 ms |
| RRF + 术语 + 精排 | 0.91 | 0.76 | 0.83 | 0.70 | 55 ms |

从向量 only（0.72）到 RRF 融合（0.85），Recall@5 提升 13 个百分点，是单步最大收益，验证了 BM25 补足精确术语匹配的价值。RRF + 术语 + 精排（0.91）再提升 6 个百分点，术语扩展解决同义词召回缺口，精排将正确结果前置。

## 9. 压测数据

并发 100 虚拟用户持续压测 10 分钟，各接口延迟与吞吐：

| 接口 | QPS | P50 | P95 | P99 | 错误率 |
|------|-----|-----|-----|-----|--------|
| POST /qa/ask（缓存未命中） | 52 | 1.2 s | 1.9 s | 2.7 s | 0.0% |
| POST /qa/ask（缓存命中 40%） | 78 | 720 ms | 1.4 s | 2.2 s | 0.0% |
| POST /qa/stream（首字延迟） | 60 | 280 ms | 520 ms | 780 ms | 0.0% |
| POST /search | 1,850 | 28 ms | 58 ms | 92 ms | 0.0% |
| POST /documents/upload | 24 | 180 ms | 240 ms | 310 ms | 0.0% |
| GET /documents（列表） | 3,200 | 12 ms | 28 ms | 45 ms | 0.0% |

压测期间资源水位：CPU 平均 62%（峰值 85%）、内存 148 GB / 256 GB、GPU 利用率 71%、磁盘 IO 38%。瓶颈出现在 LLM 生成阶段（远端 API 限速），而非本系统计算资源。

### 9.1 限流验证

将限流配额设为 20 QPS/用户，单用户以 50 QPS 发压，验证限流生效：

| 指标 | 值 |
|------|-----|
| 实际通过 QPS | 20.0 |
| 被拒 QPS | 30.0 |
| 拒绝响应码 | 429 |
| `Retry-After` 头 | 平均 1.2 s |

令牌桶限流精准生效，无超发。

## 10. 降级链路验证

主动断开各下游，验证降级行为：

| 故障注入 | 降级动作 | 检索 Recall@5 | P95 延迟 | 告警触发 |
|----------|----------|---------------|----------|----------|
| Milvus 停止 | 向量降级 pgvector | 0.88（-3 pp） | 92 ms | 是 |
| Cross-Encoder 停止 | 跳过精排，取 RRF Top-5 | 0.85（-6 pp） | 35 ms | 是 |
| Neo4j 停止 | 关系类问题回退向量+BM25 | 关系类 0.52 | 38 ms | 是 |
| Redis 停止 | 缓存与限流降级直查 | 0.91（不变） | 1.9 s | 是 |
| LLM 不可用 | offline 模式，仅返回片段 | 0.91（检索不变） | 280 ms | 是 |

降级后检索质量可预期下降，但服务持续可用，符合架构设计目标。

## 11. 结论与调优建议

### 11.1 关键结论

1. **检索质量**：默认配置（标题层级分块 + RRF + 术语 + 精排）Recall@5 达 0.91，满足企业知识库问答需求。
2. **延迟**：端到端问答 P95=1.8s，LLM 生成占近 80%；检索链路 P95=55ms，非瓶颈。
3. **吞吐**：100 并发下问答 QPS=52，检索 QPS=1,850，瓶颈在远端 LLM 限速而非本系统。
4. **弹性**：任一下游故障降级后服务持续可用，检索质量可预期退化。

### 11.2 调优建议

| 场景 | 建议 | 预期收益 |
|------|------|----------|
| 延迟敏感 | Milvus 切换 HNSW 索引 | 检索 P95 48ms → 22ms |
| 内存受限 | 保留 IVF_FLAT，调小 `nlist` | 内存降 30%，召回略降 |
| LLM 延迟高 | 启用 Query 改写结果缓存 | 改写阶段耗时降 60% |
| 同义词召回不足 | 扩充术语词典，按部门细化 | Recall@5 +2~3 pp |
| 图谱覆盖率低 | 优化实体抽取 Prompt，补全别名表 | 关系类 Recall +5 pp |
| 缓存命中率低 | 调整缓存 key 粒度（去除易变上下文） | 命中率 +10~15% |
| OCR 文档拖慢入库 | OCR Worker 独立队列 + 独立并发 | 文本类入库吞吐 +60% |

### 11.3 复现基准

cd benchmarks
