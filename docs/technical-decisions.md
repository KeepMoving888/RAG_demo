# 技术决策与权衡 (ADR)

> 面向技术评审的架构决策记录。每条决策记录背景、方案对比、最终选择与代价权衡，
> 便于后续维护者在二次开发、容量规划与故障定位时理解设计意图，避免误改核心链路。

## 概述

本文档记录企业级 RAG 知识库系统的核心架构决策（Architecture Decision Records，ADR），
覆盖检索策略、图谱融合、权限隔离、异步处理、多轮对话与降级链六个关键方向。每条决策
均给出问题背景、候选方案对比、最终选型理由与代价权衡，力求体现工程取舍的完整思考过程，
而非结果罗列。文档与 `architecture.md` / `rag-pipeline.md` / `graphrag.md` 互为补充：
前者描述"系统是什么"，本文档回答"为什么这样设计、为什么不那样设计"。

## 决策 1：混合检索策略 —— BM25 + 向量 + RRF 融合

### 背景

企业内部文档存在大量业务术语、产品代号（如 `ISM-2000`）、部门简称（如"研发一部"）
与政策编号（如《数据安全管理规范》）。这些 token 在通用语料中分布稀疏，但在企业语料中
是高频且强区分度的检索锚点。单一检索策略各有盲区：

- 纯 BM25 对术语字面命中敏感，但无法理解"部署方式"与"安装步骤"的语义等价；
- 纯向量检索能捕获语义相似，但对低频产品代号容易召回语义相近但实体不同的文档，
  且 embedding 模型对短代号（如 `ISM-2000`）的表征质量不稳定。

经实测（详见 `backend/scripts/eval_rag.py` 与 `data/seed/rag_eval_dataset.json`），
在内部评测集上纯 BM25 的 Top-5 召回率为 0.82，纯向量为 0.86，两者错误集合仅约 40%
重叠，互补空间显著。

### 方案对比

| 维度 | 纯 BM25 | 纯向量检索 | 混合检索（BM25 + 向量 + RRF） |
|------|---------|------------|-------------------------------|
| 字面匹配 | 强（TF-IDF 加权精确命中） | 弱（依赖 tokenizer 是否保留代号） | 强（BM25 路保底） |
| 语义匹配 | 弱（词面不一致即漏召回） | 强（embedding 捕获同义/近义） | 强（向量路覆盖） |
| 术语命中率 | 高（产品代号、政策号精确匹配） | 中（代号经 tokenizer 后可能被拆分） | 高（两路并集） |
| 延迟（P95） | ~30ms | ~45ms | ~70ms（两路并行 + 融合开销） |
| 运维复杂度 | 低（单进程内存索引） | 中（需维护 Milvus 集群） | 中高（两套索引 + 融合逻辑） |
| 召回率（实测 Top-5） | 0.82 | 0.86 | **0.93** |

### 决策

选择**混合检索**，两路并行召回后经 RRF（Reciprocal Rank Fusion）融合。

为何选 RRF 而非线性加权融合：

1. **分数尺度差异大**：BM25 原始分数可达数十，向量余弦相似度落在 `[0, 1]`，
   线性加权必须先做归一化（min-max / z-score），而归一化策略本身引入超参数且对
   outlier 敏感，不同查询的最优权重不同，泛化性差。
2. **RRF 基于排名而非分数**：`score(d) = Σ 1/(k + rank_i(d))`，`k=60` 为经验常数
   （Cormack et al., SIGIR 2009），天然消除尺度差异，无需调参。
3. **对 outlier 鲁棒**：排名第 1 与第 2 的贡献差为 `1/61 - 1/62 ≈ 2.66e-4`，
   而排名第 100 与第 101 仅差 `3.89e-5`，高排名差异被放大、低排名被平滑，
   与人工判断的注意力分配一致。

实现位于 `backend/app/rag/fusion.py`，模块同时保留 `weighted_fusion` 供消融对比，
但 `HybridRetriever` 默认走 RRF。

### 权衡

- **代价**：延迟增加。两路检索若串行执行，P95 延迟从单路 ~45ms 升至 ~90ms。
- **缓解**：
  - 两路并行召回（`asyncio.gather`），实测 P95 降至 ~70ms；
  - 对 BM25 倒排索引做预热，避免首次查询冷启动；
  - 对 top-k 召回结果缓存（`rag/cache.py`），命中时跳过融合阶段。

## 决策 2：GraphRAG 双路融合而非替代

### 背景

跨部门关联查询是企业知识库的高价值场景，典型问题包括：

- "ISM-2000 的认证供应商有哪些？" —— 需沿 `Product → Supplier` 边遍历；
- "负责 B 项目的人还参与了哪些项目？" —— 需沿 `Person → Project` 多跳推理；
- "研发一部发布了哪些产品的合规报告？" —— 需跨 `Department → Product → Document` 三跳。

这类问题向量检索难以覆盖：相关证据分散在不同 chunk，且证据之间的"关系"本身不体现在
文本相似度上。纯图谱检索虽能精确遍历关系，但图谱节点不含原文，需反查 `source_chunks`
回到文档，单独使用会丢失语义匹配能力。

### 方案对比

| 维度 | 纯向量检索 | 纯图谱检索 | 向量 + 图谱双路融合 |
|------|------------|------------|---------------------|
| 事实型问题（规格参数） | 强 | 弱（节点无原文） | 强（向量路主导） |
| 关系型问题（多跳推理） | 弱（证据分散） | 强（Cypher 精确遍历） | 强（图谱路主导） |
| 实体消歧 | 中 | 强（节点有唯一 ID） | 强 |
| 召回完整性 | 中（漏多跳证据） | 中（漏语义近义） | 高（互补） |
| 运维成本 | 低 | 高（Neo4j + 实体抽取 LLM） | 高 |
| 查询延迟 | ~45ms | ~60ms（含 Cypher 编译） | ~80ms（并行 + 去重） |

### 决策

选择**双路融合**。向量路负责语义匹配召回文档 chunk，图谱路负责关系推理召回关联证据，
两路结果基于 `chunk_id` 去重合并后统一送 Cross-Encoder 重排序。

路由策略（`backend/app/graphrag/fusion.py`）按查询特征分流，避免无谓图谱开销：

- 含关系词（哪些/参与了/认证了/属于/供应/管理）→ 触发图谱检索；
- 含实体名（产品代号 / 部门名）→ 双路都触发；
- 纯语义查询 → 仅向量检索，省去图谱往返延迟。

融合策略标签（`vector_only` / `graph_only` / `hybrid`）写入检索响应，便于观测与离线评估。

### 权衡

- **代价**：
  - Neo4j 运维成本（独立集群、备份、版本升级）；
  - 实体抽取准确性依赖 LLM，错抽会导致图谱边错误，反查到错误文档。
- **缓解**：
  - **图谱降级策略**：Neo4j 不可用时，`fusion_strategy` 自动标记为 `vector_only`，
    主检索链路不受影响（详见 `neo4j_store.py` 降级分支）；
  - **实体抽取置信度过滤**：抽取结果附带置信度分数，低于阈值的边不入库；
  - **图谱可灰度**：通过配置开关关闭图谱路，纯向量模式运行，便于 A/B 评估图谱增益。

## 决策 3：Milvus 分区实现部门权限隔离

### 背景

企业知识库要求"员工只能检索本部门 + 公开文档"。这是一条**安全硬约束**，不能依赖
应用层事后过滤——若向量检索先在全库召回 top-k 再过滤，当 top-k 中大量属于其他部门时，
过滤后所剩无几，召回质量塌陷；更严重的是，过滤前的中间结果可能被日志记录，形成数据泄露。

### 方案对比

| 维度 | 应用层过滤 | Collection 隔离 | Partition 隔离 |
|------|------------|-----------------|----------------|
| 隔离强度 | 弱（中间结果可见） | 强（物理隔离） | 强（检索时只扫授权分区） |
| 查询性能 | 差（全库扫 + 过滤） | 好（单 collection 小） | 好（partition_key 过滤，跳过未授权分区） |
| 部门新增成本 | 无 | 高（建 collection + 索引） | 低（建 partition 即可） |
| 跨部门查询 | 天然支持 | 需多 collection 合并 | 支持（指定多 partition） |
| 运维成本 | 低 | 高（N 个 collection 的索引/监控） | 中（单 collection 多 partition） |
| 扩展性 | 好（无结构限制） | 差（部门多时 collection 爆炸） | 好（单 collection 支持上千 partition） |
| 数据泄露风险 | 高 | 低 | 低 |

### 决策

选择 **Partition 隔离**。为每个 `department_id` 创建独立 partition，外加全局 `_public`
公开 partition。检索时只搜索 `[_public, <用户所属部门>]` 两个分区，从向量库层面保证
只返回有权限的文档。

实现位于 `backend/app/rag/milvus_store.py`，索引选型 IVF_FLAT（`nlist=128, nprobe=16`）：
精度高（FLAT 无量化损失）、构建快、内存适中，百万级 chunk 下查询延迟 <50ms。
若未来数据量达千万级且延迟要求更严，可平滑切换 HNSW，schema 不变。

### 权衡

- **代价**：分区数受 Milvus 限制（单 collection 默认 1024，可调至 4096）。企业部门数
  通常 <1000，正常情况下够用，但多租户 SaaS 场景下可能触顶。
- **缓解**：
  - **大租户独立 collection**：当单一租户的部门数超过阈值，为其分配独立 collection，
    避免单 collection partition 膨胀；
  - **分区懒创建**：部门首次上传文档时才创建 partition，避免空分区占用元数据；
  - **Milvus 不可用降级**：返回空向量结果，BM25 通路仍可用（详见决策 6）。

## 决策 4：Celery + RabbitMQ 异步文档处理

### 背景

文档入库是典型的重计算路径：一个 50MB 的 PDF 经解析、清洗、分块、向量化后，需向
Milvus 写入约 800~1200 个向量，同时向 PostgreSQL 写入分块元数据，向 Neo4j 写入
抽取的实体关系。扫描版 PDF 还需 OCR，单文件耗时可达数分钟。若在 HTTP 请求链路内
同步处理，将导致上传接口长时间占用连接、无法横向扩展，且任意一步失败需整体重跑。

### 方案对比

| 维度 | 同步处理 | FastAPI BackgroundTasks | Celery + RabbitMQ |
|------|----------|-------------------------|-------------------|
| 可靠性 | 低（进程崩溃即丢失） | 低（同进程，崩溃即丢） | 高（broker 持久化 + acks_late） |
| 可观测性 | 差 | 差（无任务状态追踪） | 强（Flower 监控 + result backend） |
| 水平扩展 | 不可扩展 | 受限于 API 进程数 | Worker 独立伸缩 |
| 重试机制 | 需手写 | 需手写 | 内置（指数退避 + 最大重试次数） |
| 任务路由 | 无 | 无 | 支持按队列分流（ingestion/embedding/graphrag） |
| 断点续跑 | 不支持 | 不支持 | 支持（每阶段结果落库） |
| 部署复杂度 | 低 | 低 | 中（broker + worker + result backend） |

### 决策

选择 **Celery + RabbitMQ**。Broker 选 RabbitMQ 而非 Redis：RabbitMQ 的消息持久化、
确认机制（`task_acks_late=True`）与优先级队列更贴合生产可靠性要求；Result Backend
用 Redis 存任务状态，与缓存共用实例但走不同 db。

任务按队列分流（`backend/app/celery_app.py`）：

- `ingestion` 队列：`parse_document`（PDF/Word/图片解析）；
- `embedding` 队列：`chunk_and_embed`（分块 + 向量化，GPU 敏感，独立 Worker）；
- `graphrag` 队列：`extract_entities_task`（LLM 实体关系抽取，耗时长）。

序列化统一用 JSON 而非 pickle，避免反序列化代码执行风险。

### 权衡

- **代价**：架构复杂度增加（broker + worker + 监控），开发与运维需理解 Celery 模型。
- **缓解**：
  - **降级模式**：RabbitMQ 不可用时，`parse_document` 退化为同步处理
    （`backend/app/ingestion/tasks.py` 检测 broker 连接失败后回退同步路径），
    保证开发环境与单机部署"即跑即用"；
  - **Flower 监控**：集成到 `monitoring/` 的 Grafana 看板，任务积压可视化告警；
  - **幂等设计**：每个任务以 `document_id` 为幂等键，重复入队不会产生重复向量。

## 决策 5：滑动窗口 + Query 改写的多轮对话

### 背景

长会话中存在两类问题：

1. **代词指代**：用户后续提问常使用"它/这个/那个"或省略主语，若直接拿原 query
   去检索，召回会因缺少实体而偏移，导致 RAG 答非所问；
2. **主题漂移**：全量历史塞入 prompt 会稀释最新问题的注意力，推高 token 成本与延迟，
   且 LLM 上下文窗口有上限。

需要平衡 token 消耗、上下文连续性与检索召回质量。

### 方案对比

| 维度 | 全量上下文 | 滑动窗口 | 滑动窗口 + query 改写 | 摘要压缩 |
|------|------------|----------|------------------------|----------|
| Token 消耗 | 高（线性增长） | 低（固定窗口） | 中（窗口 + 1 次改写 LLM 调用） | 中（摘要 token） |
| 指代消解 | 好（LLM 自行消解） | 差（窗口外指代丢失） | 好（改写时融合历史） | 中（摘要可能丢实体） |
| 主题一致性 | 好 | 差（开篇主题丢失） | 中（首尾锚点补偿） | 中 |
| 实现复杂度 | 低 | 低 | 中（需改写器） | 高（摘要质量难保证） |
| 延迟 | 高（长 prompt） | 低 | 中（+1 次 LLM） | 中（摘要需异步生成） |
| 历史可追溯 | 好 | 差（窗口外丢失） | 中（归档到 PG） | 中 |

### 决策

选择**滑动窗口（6 轮 = 3 user + 3 assistant）+ Query 改写**。

- 滑动窗口控制单次 prompt 在可预期范围，覆盖绝大多数代词指代（实测 2~3 轮即可消解）；
- Query 改写器（`backend/app/dialog/query_rewriter.py`）将当前问题与历史上下文融合，
  把"它怎么部署？"还原为"ISM-2000 怎么部署？"，使检索查询具备独立完整性；
- 额外保留首轮 user 消息作为"长程记忆锚点"，避免长会话中后期主题漂移；
- 超过 `dialog_max_turns=20` 上限后，冷数据归档到 PostgreSQL，Redis 重置为
  "首锚点 + 最近窗口"，兼顾内存占用与历史可追溯。

改写触发判定（`is_rewrite_needed`）：仅当含代词或过短（<5 字）才改写，避免对已是
完整查询的请求多花一次 LLM 调用。

### 权衡

- **代价**：query 改写增加一次 LLM 调用，端到端延迟增加 ~200ms。
- **缓解**：
  - **改写结果缓存**：以 `(session_id, 原始 query)` 为键缓存改写结果，重复提问命中缓存；
  - **三段式降级**：在线模式走 LLM 改写（质量优先），离线模式走规则改写
    （识别代词 + 上一轮主语替换，零依赖），失败兜底返回原 query 不阻断主流程。

## 决策 6：离线降级链设计

### 背景

本项目作为开源系统需要"即跑即用"——开发者克隆仓库后无需配置 PostgreSQL / Redis /
Milvus / Neo4j / LLM API 即可启动体验。但完整生产功能依赖上述外部服务，任一缺失都
不应导致系统整体不可用。这要求**全链路降级设计**：每个外部依赖不可用时自动降级，
核心功能不中断，且生产环境通过配置切换真实组件。

### 决策

采用**全链路降级设计**，每个外部依赖都有明确的降级路径，降级逻辑封装在各自模块内，
对上层调用方透明：

| 依赖不可用 | 降级行为 | 影响范围 | 实现位置 |
|------------|----------|----------|----------|
| **Milvus** | 向量检索返回空，仅 BM25 召回 | 召回率下降，链路不中断 | `rag/milvus_store.py` |
| **Neo4j** | 跳过图谱路，`fusion_strategy=vector_only` | 关系型问题召回退化为语义匹配 | `graphrag/fusion.py` |
| **LLM** | 退化为规则模板生成（拼接 top-k chunk 摘要） | 生成质量下降，仍可返回证据 | `llm/offline_llm.py` |
| **Redis** | 不缓存，对话上下文退化为进程内 dict | 仅单进程可用，多实例会话不共享 | `dialog/context_manager.py` |
| **PostgreSQL** | 元数据写内存，审计日志落本地文件 | 重启丢失，核心检索仍可用 | `database.py` |
| **RabbitMQ** | 文档处理退化为同步执行 | 入库慢，但不阻塞已有文档检索 | `ingestion/tasks.py` |
| **前端 → 后端不可用** | 前端用种子数据渲染，只读模式 | 无法上传/提问，但页面可浏览 | `frontend/src/api/seed.ts` |

降级触发统一模式：模块初始化时 `try: import xxx; _XXX_AVAILABLE = True`，
`except ImportError: _XXX_AVAILABLE = False`，运行时若 `_XXX_AVAILABLE` 为 False
或连接失败，走降级分支并记录 warning，不抛异常。

### 权衡

- **代价**：代码复杂度显著增加——每个外部依赖都要写"正常路径 + 降级分支 + 降级标记"，
  测试矩阵从 N 个组件的笛卡尔积膨胀（需覆盖各依赖单独不可用与组合不可用场景）。
- **价值**：
  - **开源即跑**：开发者零配置启动，降低上手门槛，利于社区采纳；
  - **生产可切换**：生产环境通过 `.env` 配置切换真实组件，降级分支自然失活，
    无需改代码；
  - **故障韧性**：生产环境中任一依赖故障时，系统以可预期的退化模式继续服务，
    而非整体宕机，符合架构设计目标中的"弹性可降级"原则。

## 总结

设计哲学一句话：**优先可靠性，每层都有降级，生产环境通过配置切换真实组件。**

六个决策共享同一底层逻辑——把每个外部依赖视为"可能不可用"，把每种检索策略视为
"有盲区"，通过多路融合与全链路降级，让系统在"组件齐全的生产环境"与"零配置的
开发环境"之间平滑切换，在可靠性、检索质量与运维成本之间取得工程平衡。
